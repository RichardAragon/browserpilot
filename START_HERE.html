Windows app · 1.3 preview

BrowserPilot

An AI assistant that helps set up and operate websites through their browser interfaces.

Start in three steps

  1. Open BrowserPilot.exe. Keep the adjacent _internal folder with it. Python and the CRM browser engine are included; no terminal setup is needed.
  2. Choose a model in Settings. Use your existing Codex sign-in, or add an OpenAI API key and an available structured-output model. The OpenAI path does not require Codex. Microsoft Edge is required for interactive website sign-in.
  3. Tell the assistant what you want. For example: “Connect my CRM at https://my-company.example” or “Update the City for Acme in my CRM to Austin.” The AI finds the record workspace and discovers the form. Sign in directly if prompted, or use optional locally encrypted sign-in fields. Review the actual field mapping before entry.
On the development computer: the local Dolibarr and Odoo test connections are already saved with Windows encryption. Your existing Codex sign-in is the initial model connection. Social accounts use separate app-owned browser profiles; sign in directly there.

Records beyond contacts and companies

State the object type and its name or external reference, for example: “Create a draft Sales Order called YouTube test Opportunity. Choose any existing customer.” The assistant preserves the object type, discovers the correct form and presents the real customer choice for review. A generated internal document number is left to the platform. Some platforms require creating the draft before its reference becomes editable. BrowserPilot then presents two reviews: create the draft with the selected customer, followed by updating its reference on that same draft. This path currently covers the name/reference and existing relationships, without line items. Draft creation does not validate, issue, send or pay the document.

Search and action context

Search-filter removal is recognized from the visible search region, separately from deleting a record. An unavailable navigation choice is returned to the planner so it can find another route. Existing-record dropdowns can use explicitly linked options or a unique adjacent accessible menu. These rules use rendered semantics across websites, without platform-specific adapters.

How general mode works

The model finds the broad record workspace and proposes a mapping from your field names to the actual visible controls. For creation it searches for duplicates first, opens the new form, and includes any suggested required dropdown defaults in the review. It shows the current and requested values before editing. After approval, the controller rechecks the record and mapping, records submission intent before the first field edit, applies the patch once, saves if appropriate, and reopens the form to verify. Creation also records intent before opening New, because some sites can autosave drafts. It repeats the duplicate check immediately before entry and verifies the saved record through an independent browser search or, for generated documents, by reopening its observed URL and checking its original document identity. An interrupted field-entry step may continue in its original live form after checking every approved value and establishing that final submission was not attempted. An uncertain final submission is inspected rather than repeated.

A memory for each platform

Open Connections → Platform notes. After AI setup and completed browser attempts, the model condenses local evidence into connection-specific navigation, search, creation and recovery lessons. Each lesson links to its evidence and is marked observed or tentative. The planner reads these notes on later tasks, but still uses current browser controls and the normal approval checks.

Add your own guidance or corrections in the notes view. AI updates preserve that text, and stale edits cannot overwrite a newer revision. Learn from history refreshes the lessons; revision history lets you restore an earlier version. Notes stay local with the connection, and relevant history and notes are sent to your selected model for learning and planning. Known task values are filtered from learning evidence, but this is not a guarantee that all personal information has been removed. Do not enter credentials or sensitive record data in notes.

Current boundaries

  • Salesforce, HubSpot and other website URLs are accepted; live workflows on those services have not been validated in this build. General mode is a preview, not universal guaranteed compatibility.
  • General creation and updates are available. Deletion, bulk operations and arbitrary communications remain outside its supported scope. Required select defaults can be proposed for review; other missing mandatory data may stop the task.
  • UI checks cannot provide an atomic server lock or full protection against changes made during Save. “Verified” means the requested fields were observed in the reopened UI at that time.
  • “Message visible” means the exact message persisted after reopening. It does not establish delivery or read status.
  • English interfaces and accessible DOM controls are the initial target. Inaccessible canvas controls, unrecognized dialogs, account challenges or changed layouts may require manual navigation or stop the task.

Your data and model connection

App data is stored in %LOCALAPPDATA%\BrowserPilot: history, screenshots, operation journals and browser profiles. CRM passwords and API keys are encrypted with Windows DPAPI for the current user. The package contains no account credentials or signed-in profiles. Keep your app data private; browser profiles can carry active sessions.

The selected model receives the task and relevant visible UI observations. The OpenAI transport uses the Responses API with structured outputs and store: false. Model calls are separate from platform changes: CRM and messaging updates use browser interaction only. See the official structured-output documentation.

Creation and interrupted sessions

If an opening or submission has an uncertain result, BrowserPilot will inspect that original operation instead of creating again. A lost, unsubmitted creation form may remain uncertain and require manual review; it is never silently replaced with another new form. Duplicate searches are limited by the current user’s visibility and the rendered search scope. They cannot provide server-enforced uniqueness or prevent a simultaneous external create.

Daily use

  • Stopping: use Stop task. A submitted change may still finish; use Check outcome / retry afterward.
  • Restarting: launch the executable again. An unfinished task remains interrupted and does not automatically resubmit.
  • Quitting: choose How it works → Quit BrowserPilot. Closing the dashboard tab alone leaves the local app running.
  • Sign-in issue: open the connection browser, complete sign-in or the challenge yourself, then inspect/verify again.
  • Model issue: use Settings to check provider, model ID and key or Codex sign-in. API billing and Codex account limits are separate from this app.
